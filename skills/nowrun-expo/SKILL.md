# nowrun SDK for React Native apps (Expo and bare)

The nowrun SDK lets an AI agent (today, ChatGPT with the nowrun plugin) operate an Android app on the user's behalf, through functions the app exposes. In a
React Native app, the `nowrun-expo` module carries calls from the native SDK into JavaScript: you
declare the functions (`ToolSpec[]`), give one handler per function, and push the app's state
as it changes. nowrun connects to whichever app is in the
foreground, reads its function list, and calls the functions.

The functions are chosen by the agent, an LLM: it decides which function to call,
and with what arguments, from the app's state and the function list the app publishes, meaning
each function's name and description and each argument's name, type and description. It can't
see the app's code. So write the list like instructions for that agent: vague descriptions
lead to wrong calls (see 3.6).

Follow the same seven phases whether the app already exists or is being built now. For an app
still in development, run phases 3 to 6 again whenever a feature is added, so its functions
ship with the feature.

1. Integrate the SDK
2. Analyse the app
3. Design the functions
4. Implement the functions layer
5. Report state
6. Verify
7. Hand over

## Phase 1 — Integrate the SDK

**Which kind of React Native app is it?** Two checks, and each decides something different.
Make both on every run, since the answers can change between runs.

- **Is `android/` maintained by hand?** Run `git ls-files android | head -1` in the app's
  root. If it prints a path, the app keeps its own native project in git: a bare React Native
  app, or an Expo app on the bare workflow. **Never run `npx expo prebuild` on it**: prebuild
  generates `android/` and would overwrite the hand-made changes. The steps marked **Bare RN**
  apply. If it prints nothing, `android/` is generated by `npx expo prebuild` (or doesn't exist
  yet), and the steps for an Expo app apply. If the project isn't in git, ask the user which it
  is.
- **Is `expo` a dependency in `package.json`?** If it isn't, add Expo's module system first:
  `nowrun-expo` is built on the Expo Modules API (`expo-modules-core` and its Gradle plugin).
  This adds only the module runtime and autolinking, not the rest of Expo:

  ```bash
  npx install-expo-modules@latest
  ```

  It installs the `expo` package in the version matching the app's React Native version,
  hooks Expo autolinking into `android/settings.gradle`, and registers Expo modules in
  `MainApplication`. Review its diff, then run the app once to confirm it still builds before
  going on. The React Native version must be one a current Expo SDK supports; for very old
  versions (roughly before 0.70), upgrade React Native first. Because it adds `expo` to
  `package.json`, the next run finds an Expo dependency, but `android/` is still the app's own:
  that's why the first check, not this one, decides about prebuild.

The steps that differ when `android/` is maintained by hand (building, `minSdk`, a local debug
run) are marked **Bare RN** where they come up.

**Get the package.** The module is one npm tarball. It isn't on the public npm registry, so
`npm install nowrun-expo` won't find it; download it instead. The tarball already contains the
SDK (`android/libs/nowrun-sdk.jar`) and the compiled JS and types; there's nothing to build. If
the download fails, ask the user; don't substitute another package.

Keep the tarball inside the app's repo, so teammates and automated build servers (CI) can
install it:

```bash
mkdir -p vendor && curl -fL -o vendor/nowrun-expo.tgz https://downloads.nowrun.io/latest/nowrun-expo.tgz
```

Install it with the package manager the app already uses, which its lockfile shows. Never use
another one: that adds a second lockfile and splits the install.

| Lockfile | Install | Update |
|---|---|---|
| `package-lock.json` (npm) | `npm install ./vendor/nowrun-expo.tgz` | `rm -rf node_modules/nowrun-expo && npm install ./vendor/nowrun-expo.tgz` |
| `yarn.lock`, and `yarn --version` is 1.x | `yarn add file:./vendor/nowrun-expo.tgz` | `yarn cache clean && rm -rf node_modules/nowrun-expo && yarn add file:./vendor/nowrun-expo.tgz` |
| `yarn.lock`, and `yarn --version` is 2 or later | `yarn add ./vendor/nowrun-expo.tgz` | `yarn install` |
| `pnpm-lock.yaml` | `pnpm add ./vendor/nowrun-expo.tgz` | `rm -rf node_modules/nowrun-expo && pnpm add ./vendor/nowrun-expo.tgz` |
| `bun.lock` or `bun.lockb` | `bun add ./vendor/nowrun-expo.tgz` | `bun remove nowrun-expo && bun add ./vendor/nowrun-expo.tgz` |

`package.json` gains a `nowrun-expo` entry pointing at `vendor/nowrun-expo.tgz`. Commit
`vendor/nowrun-expo.tgz` together with `package.json` and the lockfile. The installed copy in
`node_modules/nowrun-expo` is ready-built, compiled output; never edit it.

**Updating the module:** download it again over `vendor/nowrun-expo.tgz` with the same `curl`
command, then run the update command from the table. A plain reinstall isn't enough: the
version often stays the same, so the package manager keeps the copy it already has. With Yarn 1,
`yarn cache clean` empties Yarn's whole download cache, so later installs download again.

**It needs its own build, not Expo Go.** The module is native, so the app must be compiled
into its own APK. Your job is to confirm the app compiles with the module and the functions
layer:

```bash
npx tsc --noEmit
npx expo prebuild --platform android       # generates android/; re-run after adding native packages
cd android && ./gradlew assembleDebug
```

**Bare RN**: there's no prebuild step, since `android/` is the app's own. Run `npx tsc --noEmit`
(if the app uses TypeScript), then `cd android && ./gradlew assembleDebug`; autolinking picks
up the module.

Stop at this check. Getting the app onto nowrun is covered separately, not by this skill,
so don't attempt it or make up steps for it, and don't change the app's build setup.

For quick UI work on a local phone or emulator, `npx expo run:android` (Expo) or
`npx react-native run-android` (**Bare RN**) still works: it's a debug build that loads its JS
from Metro. nowrun isn't there, so the SDK never connects.

In Expo Go, or on any platform other than Android, the module's native part is missing, and
`useNowrun` and `notifyState` quietly do nothing, so no `Platform` checks are needed. The
module also exports `isAvailable` (`import { isAvailable } from 'nowrun-expo'`), which is
`false` in that case and `true` when the native part is in the build. `true` only means the
module is present, not that the app is connected to nowrun. Most apps never need it.

**Nothing to add to the manifest.** The module declares the `NowrunSdkService` `<service>` and
the `<queries>` entry for nowrun. `minSdk` must be 24 or higher: the Expo default, and in a **Bare RN** app check `minSdkVersion` in
`android/build.gradle`.

**No R8 rules needed.** The module brings the SDK's own rules with it, so a minified release
build keeps everything it needs. Don't add rules of your own for it.

**How it behaves at runtime:**
- Only the app in the foreground is connected. Going to the background disconnects it, and
  the next resume reconnects.
- Handlers run on the JS thread. A handler can return its reply directly, or be an
  `async` function that returns a promise; then the reply is sent once the promise settles.
  Every call is answered: a throw or rejection becomes `APP_FUNCTION_FAILED`, and a handler
  that returns nothing replies `null` (development builds warn about it).
- On a device without nowrun (any ordinary phone or emulator), the SDK never
  connects. Each time the app comes to the foreground it retries once a second, up to 10
  times, logging two lines: `nowrun service not found, retrying every 1000ms, up to 10 times`
  and, 10 seconds later, `nowrun service not found, gave up after 10 attempts`. That's
  expected, not an error.

## Phase 2 — Analyse the app

Read the code before designing anything. Build an inventory of four things. The same
questions apply to a finished app and to a plan for a new one.

| Inventory | What it is | Where to look |
|---|---|---|
| **Screens** | Every place a user can be: routes, tabs, drawer entries, modals, in-component "tabs" held in `useState` | `app/` directory (expo-router file routes and `_layout.tsx` tab/stack groups), `createNativeStackNavigator`/`createBottomTabNavigator` screens, `useState` holding a current tab or step |
| **Entities** | The app's own things with an identity that users see and act on: products, songs, notes, orders, levels, contacts | TypeScript types/interfaces with an `id`, store slices (zustand, redux, context), API clients, data files, `FlatList` item types |
| **Actions** | Everything a user can do: every `onPress`, `onSubmit`, `onChangeText` that commits, swipe, toggle | Components' event props, store actions and reducers, custom hooks the UI calls |
| **Choices** | Finite option sets: sort orders, categories, sizes, modes, filters | String-literal unions (`type Sort = 'price' \| 'name'`), `enum`s, `as const` arrays, segmented-control options |

Also note:
- **Deep links:** `scheme` in `app.json` and the `linking` config. They show how the app
  already opens specific content, so reuse them for navigation.
- **Gated flows:** login, payment, account deletion, and anything that sends to other people.
- **Long operations:** uploads, renders, syncs.
- **The single source of truth:** the store or reducer that both the UI and your handlers
  must go through.

Write the inventory down. For an existing app, show it to the user with the function list
from phase 3 before implementing, so they can cut or add functions.

## Phase 3 — Design the functions

Each part of the inventory maps to a kind of function: actions become action functions,
entities become search and open functions, choices become fixed value lists, and screens
become navigation.

### 3.1 The baseline every app exposes

| Function | Purpose |
|---|---|
| `get_state` | Where the user is and what they see. Return exactly the payload phase 5 pushes. |
| `open_screen(screen)` | Go to a top-level screen. `screen` is a `String` with `values` covering every screen from the inventory. |
| `go_back` | Back navigation. |
| `open_<entity>(id)` | Open an entity's detail screen, for each entity that has one, e.g. `open_product(id)`. |
| `search_<entities>(query, …filters)` | Find entities and return their ids. Every other function takes ids, not names. |

Navigation functions move the user and change nothing else. An agent can't press a button
on a screen it can't reach, so full navigation coverage comes first.

### 3.2 Actions

- **One function per distinct action.** Use parameters for its variations. Write
  `set_sort(order)`, not `sort_by_price` plus `sort_by_name`.
- **Name it verb + noun in `snake_case`,** for functions and arguments alike: `add_to_cart`,
  `product_id`.
- **Go through the same code the UI uses,** the store action or dispatcher the button's
  `onPress` calls. Never reimplement the logic.
- **Respect the UI's rules.** If the UI requires login, a selected item or an unlocked level,
  the function does too, and returns an error explaining what's missing.
- **Keep the arguments few.** nowrun refuses a call unless it has exactly one value per
  argument, sent in declaration order, so every argument must be sent on every call, including
  optional ones (as `""` or `null`). Each extra argument is another chance for the agent to get
  a call wrong. If a function needs many, it's usually several actions: split it, or group
  related values into one `JSONObject` argument with declared `fields`.
- **Put an entity's id in the argument, not its name.** When only a name is known, the agent
  calls `search_…` first.

### 3.3 Content (entities)

For each entity that users act on:
- `search_<entities>(query, …filters)` returns the matching items, each
  `{id, name, …}` with a few key fields, matched by text, with suggested results when `query`
  is empty. The whole reply must stay under 128 KiB, or the call fails with
  `RESULT_TOO_LARGE`, so for lists that can grow large, return a bounded number and take a
  `limit` or `page` argument.
- `get_<entity>(id)`, if the detail isn't obvious from search results.
- **Ids must be stable.** Use the database or server id, never a position in a list. The
  agent gets an id from one call and uses it in a later one, e.g. `search_products("mug")`
  returns `[{"id": "p_1042", "name": "Blue Mug"}, {"id": "p_2201", "name": "Red Mug"}]`,
  then `add_to_cart("p_1042", 1)`. A position ("item 0") changes whenever the list is
  re-sorted, filtered or added to, so by the second call it can point at a different item,
  and the wrong one gets changed without any error.
- **Put what's on screen in state,** as `{"id", "name"}` in display order. Users talk about
  what they see, and state is how the app tells the agent what that is. With
  `"visible": [{"id": "p_1042", "name": "Blue Mug"}, {"id": "p_2201", "name": "Red Mug"}]`,
  "open the second one" becomes `open_product("p_2201")`, and "add the red mug" matches the name.
  Use the same stable ids, so the agent can pass them straight to other functions.

### 3.4 Safety: confirmation, permissions, undo

- **Irreversible or outward-facing actions** (delete, purchase, send, post, overwrite) take a
  final `confirm` `boolean` argument. With `confirm` false, change nothing and return
  `NEEDS_CONFIRMATION` with a one-line summary of what would happen.
- **Never expose** credential entry, payment-detail entry, security or permission settings,
  or anything that bypasses a paywall or login.
- **Ambiguity:** if a lookup matches more than one entity, return `AMBIGUOUS` with the
  candidates (`id` and `name`) instead of guessing.
- **Undo:** if the app has undo, expose `undo`.

### 3.5 Long operations

nowrun accepts one unresolved call per session and answers any other with `BUSY`, so
handlers must settle quickly, ideally under 2 seconds. For long work (uploads, renders),
start it without awaiting it, return `{ started: true }` right away, and report progress and
the outcome through state (`upload: { status: 'running', percent: 40 }`).

**Every call must be answered.** An unanswered call holds the session, and every later call
gets `BUSY` for 60 seconds. Then nowrun gives up on it and reports it as `unknown` with
`APP_RESULT_TIMEOUT`, so the agent may never learn whether it worked. A call goes unanswered
when its handler returns a promise that never settles, e.g. one waiting for the user to tap
something. The module answers everything else for you, but not usefully:
- a handler that returns nothing (`undefined`) replies `null`, and development builds warn
  about it. The agent learns nothing, so always `return ok(...)` or `fail(...)`, even from a
  handler with nothing to report: `return ok('done')`;
- a value `JSON.stringify` can't encode (a `BigInt`, an object with a cycle) becomes an
  `APP_FUNCTION_FAILED` reply, even though the work was done. Return plain data.

### 3.6 Descriptions

The descriptions are what the LLM reads, so write them as instructions:
- **`functionDescription`:** what it does, its side effects, what it returns, and when to use
  it instead of a similar function.
- **Argument `description`:** its meaning, format, range or allowed values, how to skip it,
  and an example. Arguments keep their real names in the contract, so don't repeat the name.

Keep the whole function list under 128 KiB; a bigger one is refused with `CATALOG_TOO_LARGE`
and no function can be called. Don't paste every valid id into a description; that's what
`search_…` is for.

## Argument types

Read [references/argument-types.md](references/argument-types.md) before writing any
`ToolSpec`. It has the full table; each type in it converts the same way every time, so calls
don't fail on their arguments. In short:
- ids, free text, dates (ISO 8601), colors (`#RRGGBB`) and URLs are `'String'`; choices are
  `'String'` with `values`;
- whole numbers are `'int'`, decimals `'number'`, yes/no `'boolean'`, lists `'String[]'`;
- optional text is sent as `""` to skip, optional numbers, flags and lists as `null`; either
  way the key is missing from `args`, so give it a default in the handler;
- never `'long'` for ids, no `JSONObject` without `fields`, no custom type names, and as few
  arguments as the action needs.
- Always pass `tools` to `useNowrun` (`useNowrun(handlers, { tools: TOOLS })`), with one
  `ToolSpec` per handler: without it the agent sees no argument names or types.

## Phase 4 — Implement the functions layer

Create a `nowrun/` folder holding:
- `tools.ts`, the declarations;
- `results.ts`, the reply helpers;
- `useAppFunctions.ts`, which builds the handlers;
- `navigation.ts`, the one place handlers reach the navigator through.

Wire it up once in the root component.

### Where app state must live

A handler must return the outcome of what it did, but `setState` is asynchronous, so a
handler can't read React state back after calling it. Keep the state the functions touch in
something readable synchronously:
- a store: zustand's `useStore.getState()`, or redux's `store.getState()`;
- or one dispatcher that both the UI and the handlers call, which returns the result along
  with the new state.

If the state is spread across `useState` calls, lift it into a reducer or store first, using
the same code path the UI already uses.

### Replies

Every handler returns `ok(response)` or `fail(code, message)` from `results.ts`. Only
`response` reaches the caller. Use these error codes, with a message that says how to fix the
call: `INVALID_ARGUMENTS`, `NOT_FOUND`, `AMBIGUOUS`, `NEEDS_CONFIRMATION`, `NOT_ALLOWED`,
`APP_FUNCTION_FAILED`.

Read [references/replies.md](references/replies.md) for `results.ts`, when to use each code,
and how nowrun reads a reply: only an envelope can fail a call, and a raw object with
its own `success` field is misread.

### Code

- [references/code.md](references/code.md) has a complete `tools.ts` and
  `useAppFunctions.ts` to adapt: the baseline functions, a search, an action and a
  confirmed destructive action.
- [references/navigation.md](references/navigation.md) has `navigation.ts` for React
  Navigation and for expo-router, and what to do with tabs held in `useState`.

### Wiring: once, in the root

Call `useNowrun` in a component that stays mounted for the app's whole life: `App.tsx`, or
the root `app/_layout.tsx` with expo-router.

```tsx
import { useNowrun } from 'nowrun-expo';
import { TOOLS } from './nowrun/tools';
import { useAppFunctions } from './nowrun/useAppFunctions';

export default function App() {
  useNowrun(useAppFunctions(), { tools: TOOLS });
  // ...
}
```

- **Handlers can change.** They're held in a ref, so each render's handlers are the ones
  that answer.
- **`tools` is read once, at mount.** Keep the function list static. When a function isn't
  available right now (signed out, wrong screen), keep it declared and return `NOT_ALLOWED`;
  don't add and remove functions.
- **Call it once.** If it's mounted more than once, the most recently mounted one answers
  (development builds warn); while none is mounted, calls are answered `NOT_ALLOWED`.

## Phase 5 — Report state

Push state whenever anything the user could see changes, including navigation:

```ts
import { notifyState } from 'nowrun-expo';

// e.g. subscribe once at the root:
useEffect(() => useShop.subscribe(() => notifyState(snapshot())), []);
// ...and call it from NavigationContainer's onStateChange, or when usePathname() changes.
```

nowrun gives the pushed state to the agent: it says what's on screen and what it means (ids,
selection, work in progress). `get_state` returns `snapshot()` too, so pulled and pushed state never disagree.
Build it from the store and the current route, never from values captured by a render. Keep it
small: nowrun refuses a state over 128 KiB.

```json
{
  "screen": "product",
  "screen_params": {"id": "p_1042"},
  "visible": [{"id": "p_1042", "name": "Blue Water Bottle"}],
  "selection": null,
  "cart_count": 3,
  "signed_in": true,
  "last_action": "Added Blue Water Bottle to cart",
  "tasks": {"upload": {"status": "running", "percent": 40}}
}
```

- `screen` uses the same values `open_screen` accepts; detail screens add `screen_params`.
- `visible` lists the entities on screen in display order: only what's actually visible,
  not the whole list behind it.
- `last_action` is a human-readable line saying what just changed; showing it in a toast
  also helps the user.
- `tasks` holds long operations in progress.

If the store changes rapidly (typing, sliders), debounce the push to about 200 ms. It's safe
to call while nothing is connected: state reported while disconnected is held and delivered
when the app connects.

**Push it again whenever the app returns to the foreground.** nowrun clears its copy of
the app's state each time the app connects, which happens on every return to the foreground,
and state already delivered is not sent again. Without this, nowrun has no state until
the next change:

```ts
import { AppState } from 'react-native';

useEffect(() => {
  const sub = AppState.addEventListener('change', (s) => s === 'active' && notifyState(snapshot()));
  return () => sub.remove();
}, []);
```

## Phase 6 — Verify

1. **Check that it compiles:** `npx tsc --noEmit`, then `cd android && ./gradlew assembleDebug`
   (after `npx expo prebuild --platform android` in an Expo app) must succeed.
2. **Watch development warnings** in a local debug run, if a phone or emulator is connected
   (`adb devices`; skip steps 2 and 3 otherwise): `npx expo run:android`, or
   `npx react-native run-android` for **Bare RN**. Metro logs `[nowrun-expo] declared but not handled: …` or
   `handled but not declared, so unreachable: …` when `TOOLS` and the handlers disagree. Fix
   every one. These warnings come from the JS side, so they show up without nowrun.
3. **Check that the SDK starts,** in the same local debug run: with the app in the
   foreground, run `adb logcat -s NowrunSdkService`. You should see
   `nowrun service not found, retrying every 1000ms, up to 10 times`, then `gave up after 10 attempts`.
   That confirms the native SDK started while the app was in front; nowrun isn't
   there locally, so nothing else is logged. If there's no output at all, `useNowrun` isn't mounted,
   or the build doesn't include the native module (Expo Go). Also look for
   `not publishing …` warnings: the SDK left out a tool with an empty `functionName`, an
   argument with an empty `name`, or a repeated `functionName`. Fix every one.

**Testing on nowrun is done by the user.** Getting the app onto nowrun and having nowrun
call the functions aren't covered by this skill: don't attempt them or invent steps for
them. Instead, write the user a test plan to run on nowrun, covering:
- **each function** with valid arguments; a wrong type (`"abc"` for an `int`); an
  out-of-range value; an unknown id; a value outside `values`; and, for destructive functions,
  `confirm` false. Each failure must come back with a code from the error-code table and a
  message saying how to fix the call; after each success, the screen and pushed state must
  match the reply;
- **navigation:** `open_screen` for every value, `open_<entity>` for every entity, and
  `go_back`. Each must land on the right screen and report it in state;
- **if the app is minified:** that the minified build still connects.

## Phase 7 — Hand over

Tell the user:
- that the app compiles, and the test plan from phase 6;
- which functions were added, grouped as navigation, content and actions;
- what was deliberately left out and why (credentials, payments, anything gated);
- where the functions layer lives (`nowrun/`), and the rule for new features: every new
  screen gets an `open_screen` value, and every new user action gets a function or an
  argument on an existing one;
- that `nowrun-expo` comes from `vendor/nowrun-expo.tgz`: to update, download it again from
  `https://downloads.nowrun.io/latest/nowrun-expo.tgz` over that file, and reinstall it.

## Checklist

- [ ] If `expo` wasn't a dependency: `npx install-expo-modules` was run and the app still builds.
- [ ] If `android/` is in git: `npx expo prebuild` was never run.
- [ ] The module was installed with the app's own package manager, and there's still only one
  lockfile.
- [ ] `nowrun-expo` is installed from `vendor/nowrun-expo.tgz`, which is committed; the app runs as its own build, not Expo Go.
- [ ] `useNowrun(handlers, { tools: TOOLS })` is called once, in a component that's always mounted.
- [ ] Baseline is complete: `get_state`, `open_screen` with `values` covering every screen, `go_back`, `open_<entity>`, `search_<entities>`.
- [ ] Every function has a `functionDescription` and every argument a `description`.
- [ ] Only types from the common-types table; choices use `values`; few arguments; ids are strings.
- [ ] Handlers return `ok()`/`fail()` with the standard error codes, and go through the same store actions as the UI.
- [ ] App state that handlers touch is readable synchronously (a store or dispatcher), not only in `useState`.
- [ ] Destructive actions take `confirm`; credentials and payments aren't exposed.
- [ ] State is pushed on every change, including navigation, and whenever the app returns to the foreground; `get_state` returns the same shape.
- [ ] Every handler's promise settles; none waits for the user.
- [ ] No `[nowrun-expo]` warnings; the app compiles (`assembleDebug`) with no build setup changes made; the user has a test plan covering every function (valid and invalid arguments) and every navigation target.
